## Architecture Overview

ClipCash uses a **custom, dependency-free i18n system** — no third-party library (no next-intl, next-i18next, or react-i18next). It is built entirely inside `app/lib/i18n/` and consists of four files:

```
app/lib/i18n/
├── types.ts          # Locale, LocaleConfig, I18nContextType interfaces
├── translations.ts   # Core translate() engine + community translation registry
├── I18nProvider.tsx  # React context + locale persistence + browser detection
└── locales/
    ├── en.json       # English — the canonical base schema
    ├── es.json       # Spanish
    ├── fr.json       # French
    ├── de.json       # German
    ├── ar.json       # Arabic (RTL)
    └── pt.json       # Portuguese
```

### How it fits together

```
app/layout.tsx
  └── <I18nProvider>          ← mounts at root, wraps the entire app
        ├── reads localStorage["clipcash_locale"] on mount
        ├── falls back to detectBrowserLocale()
        └── provides I18nContext to all client components

Client component
  └── useI18n()               ← consumes the context
        └── t("some.key", { param: value })
              └── translate() in translations.ts
                    ├── looks up key in active locale dict
                    ├── falls back to en.json if key is missing
                    └── returns the raw key if not found anywhere
```

> **Server components**: The i18n context is client-only (`"use client"`). React Server Components cannot call `useI18n()` or `t()`. SSR renders the page with `lang="en"` in the `<html>` tag; `I18nProvider` corrects this on the client via `document.documentElement.lang`.

### Supporting files

| File | Purpose |
|---|---|
| `components/common/LanguageSwitcher.tsx` | UI dropdown to switch locale; shows detected locale, RTL badge, community badge |
| `components/common/CommunityTranslationModal.tsx` | In-browser tool to upload, preview, and submit a new locale |
| `app/api/i18n/contribute/route.ts` | `GET` returns the `en.json` template; `POST` accepts and validates community submissions |
| `scripts/validate-translations.js` | Node script that checks all locale files for missing keys vs. `en.json` |
| `__tests__/lib/i18n.test.ts` | Unit tests for `translate()`, `detectBrowserLocale()`, fallback behavior |

## Supported Locales

Six locales are bundled with the application:

| Code | Language | Native Name | Direction | Flag |
|------|----------|-------------|-----------|------|
| `en` | English | English | LTR | 🇺🇸 |
| `es` | Spanish | Español | LTR | 🇪🇸 |
| `fr` | French | Français | LTR | 🇫🇷 |
| `de` | German | Deutsch | LTR | 🇩🇪 |
| `ar` | Arabic | العربية | **RTL** | 🇸🇦 |
| `pt` | Portuguese | Português | LTR | 🇧🇷 |

RTL is also supported for `he` (Hebrew), `fa` (Farsi), and `ur` (Urdu) if a locale file is added — the RTL detection set in `I18nProvider.tsx` already covers these codes.

Additional locales can be added at runtime via the [community translation tool](#community-translation-tool) without a code change, or permanently via [a pull request](#adding-a-new-locale-pr-workflow).

## Using Translations in Components

### The `useI18n` hook

```tsx
import { useI18n } from "@/app/lib/i18n/I18nProvider";

export default function MyComponent() {
  const { t, locale, setLocale, locales, dir, isRTL } = useI18n();

  return <p>{t("common.loading")}</p>;
}
```

The hook throws if called outside `<I18nProvider>`, which is mounted at root, so this is only a concern in isolated tests (wrap with `<I18nProvider>` in your test render helper).

Full context shape (`I18nContextType` in `types.ts`):

| Property | Type | Description |
|---|---|---|
| `t` | `(key, params?) => string` | Translate a key with optional interpolation |
| `locale` | `Locale` | Active locale code, e.g. `"en"` |
| `setLocale` | `(locale) => void` | Switch the active locale |
| `locales` | `LocaleConfig[]` | All available locales (built-in + community) |
| `dir` | `"ltr" \| "rtl"` | Text direction for the active locale |
| `isRTL` | `boolean` | Shorthand for `dir === "rtl"` |
| `registerLocale` | `(config, dict) => void` | Register a community translation at runtime |
| `detectedLocale` | `string \| null` | The locale auto-detected from the browser |

### Key naming & namespaces

Translation keys use **dot-notation** to traverse the nested JSON structure. Top-level keys are logical namespaces:

| Namespace | Covers |
|---|---|
| `common` | Shared labels (loading, error, close, copy, …) |
| `dashboard` | Dashboard page strings |
| `wallet` | Wallet connection, send, balance UI |
| `activity` | Transaction activity feed |
| `earnings` | Earnings summary |
| `fee_sponsorship` | Stellar fee sponsorship UI |
| `transform` | Style transformation panel |
| `notifications` | Notification titles |
| `sync` | Offline / sync banner |
| `comparison` | Clip comparison view |
| `brand_kit` | Brand kit manager |
| `voiceover` | Voiceover recorder |
| `i18n` | Language switcher and contribution UI |

Always use an existing namespace before creating a new one. New namespaces require a matching top-level key in every locale file.

### Interpolation

Embed dynamic values using `{paramName}` placeholders:

```json
// en.json
"activity": {
  "showing": "Showing {count} of {total} transactions",
  "minutes_ago": "{minutes}m ago"
}
```

```tsx
t("activity.showing", { count: 5, total: 42 })   // "Showing 5 of 42 transactions"
t("activity.minutes_ago", { minutes: 3 })          // "3m ago"
```

Rules for interpolation:
- Placeholder names must be **identical** across all locale files.
- Placeholder order in the string can differ between languages — the substitution is by name, not position.
- Never pass raw user input directly as an interpolation value without sanitizing it first.

> **No pluralization engine**: The i18n system does not handle plural forms. For now, pluralization is handled in application code. When adding new strings that vary by count, prefer phrasing that avoids grammatical plural changes where possible (e.g., "Showing {count} items" rather than "Showing {count} item/items").

### RTL layout

When an RTL locale is active, the provider sets:

```
document.documentElement.dir = "rtl"
document.documentElement.lang = "<locale>"
```

Components can consume `isRTL` or `dir` from `useI18n()` to apply directional CSS adjustments:

```tsx
const { isRTL } = useI18n();
<div className={isRTL ? "flex-row-reverse" : "flex-row"}>…</div>
```

Prefer CSS logical properties (`margin-inline-start`, `padding-inline-end`, `text-align: start`) in Tailwind or CSS modules over physical properties (`ml-`, `pr-`, `text-left`) so that RTL reflow happens automatically without conditional class names.

## Locale Detection & Persistence

On first load (before a user makes a manual selection), the provider follows this priority order:

1. **Saved preference** — `localStorage["clipcash_locale"]` if it holds a known locale code.
2. **Browser detection** — `navigator.languages` is iterated; each entry is matched against the six supported codes, first by exact match (`"ar"`) then by language prefix (`"ar-EG"` → `"ar"`).
3. **Fallback** — `"en"`.

When the user changes language via the `LanguageSwitcher`, the new code is saved to `localStorage["clipcash_locale"]` immediately.

Community locale registrations (uploaded via the in-app tool) are persisted separately in `localStorage["clipcash_custom_locales"]` as a JSON array of `{ config, translations }` objects, and restored on the next page load.

## Translation File Structure

All locale files are flat-namespace JSON files in `app/lib/i18n/locales/`. The English file (`en.json`) is the **canonical schema** — every other locale file must contain the same set of keys.

Example snippet:

```json
{
  "wallet": {
    "connect": "Connect Wallet",
    "sending": "Sending...",
    "showing": "Showing {count} of {total} transactions"
  },
  "common": {
    "loading": "Loading...",
    "error": "Error"
  }
}
```

A few structural rules:
- **Two levels max**: `namespace.key`. Deeper nesting is allowed where it aids organisation (e.g., `transform.style.anime.name`) but avoid going beyond three levels.
- **String values only** at the leaf level — no arrays, booleans, or numbers.
- **Preserve all keys** when copying `en.json` as a template. Missing keys fall back to English at runtime, but the validation script treats them as errors.

## Translation Guidelines

Follow these guidelines when writing new strings or translating existing ones.

### Writing new English strings

1. **Add the key to `en.json` first.** Then add the same key (translated) to every other locale file, or leave the translation for a later PR and note the missing coverage.
2. **Use sentence case**, not title case. `"Connect wallet"` not `"Connect Wallet"` — unless the string is a button label or heading where title case is the UI standard.
3. **Keep strings short.** UI labels should fit comfortably in the smallest target language. German and Finnish compound words can be 40–60% longer than English equivalents.
4. **Do not concatenate translated strings in code.** Grammatical word order differs between languages. Use interpolation instead:
   ```tsx
   // Bad
   t("wallet.balance") + ": " + amount
   
   // Good — add a key "wallet.balance_value": "Balance: {amount}"
   t("wallet.balance_value", { amount })
   ```
5. **Avoid idioms and cultural references** that do not translate cleanly.
6. **Use gender-neutral phrasing** where the language allows it.

### Translating strings

1. Preserve every `{placeholder}` exactly as written — same name, same braces.
2. Do not translate proper nouns: `Stellar`, `XLM`, `Friendbot`, `MetaMask`, `Phantom`, brand names.
3. Maintain the same punctuation style (trailing ellipsis `…` on loading states, `!` on success messages).
4. If a concept does not exist in the target language, use a descriptive phrase rather than leaving the English word untranslated. If the English term is widely understood in the tech community (e.g., "NFT"), it may be kept as-is with a note in the PR.
5. For RTL languages: do not manually reverse word order — the browser and CSS handle visual mirroring. Write text in natural reading order for that language.

### Reviewing translations

PRs that add or modify locale files should have at least one reviewer who is a native or near-native speaker of that language. If no such reviewer is available in the maintainer team, note this in the PR description and request community review.

## Adding a New Locale (PR Workflow)

Follow these steps to permanently add a new built-in locale.

### 1. Create the locale JSON file

Copy `en.json` to `app/lib/i18n/locales/<code>.json` (e.g., `it.json` for Italian):

```
cp app/lib/i18n/locales/en.json app/lib/i18n/locales/it.json
```

Translate every string value. Keep all keys and all `{placeholder}` tokens intact.

### 2. Register the translation in `translations.ts`

```ts
// app/lib/i18n/translations.ts
import it from "./locales/it.json";

const translations: Record<string, Record<string, any>> = {
  en, es, fr, de, ar, pt,
  it,   // ← add here
};
```

### 3. Add the locale config in `I18nProvider.tsx`

```ts
// app/lib/i18n/I18nProvider.tsx
const DEFAULT_LOCALES: LocaleConfig[] = [
  // … existing entries …
  { value: "it", label: "Italian", nativeName: "Italiano", direction: "ltr", flag: "🇮🇹" },
];
```

For RTL languages, set `direction: "rtl"`. The provider and `LanguageSwitcher` will handle the rest automatically.

### 4. Update the `Locale` type (if needed)

The `Locale` type in `app/lib/i18n/types.ts` accepts any `string`, so this step is optional, but adding the code as a literal keeps TypeScript strict:

```ts
// app/lib/i18n/types.ts
export type Locale = "en" | "es" | "fr" | "de" | "ar" | "pt" | "it" | string;
```

### 5. Validate key coverage

```bash
node scripts/validate-translations.js
```

Or with the npm script:

```bash
npm run validate:translations
```

The script exits with code 1 and prints every missing key if coverage is not 100%. Fix all reported keys before opening the PR.

### 6. Run the existing tests

```bash
npm test __tests__/lib/i18n.test.ts
```

Add test cases for the new locale — at minimum, verify a few keys load correctly and that missing keys fall back to English:

```ts
// __tests__/lib/i18n.test.ts
it("translates a key in Italian", () => {
  expect(translate("it", "common.loading")).toBe("Caricamento...");
});

it("falls back to English for a missing Italian key", () => {
  expect(translate("it", "common.some_new_key")).toBe("Some new value");
});
```

### 7. Open the pull request

- Title: `i18n: add Italian (it) locale`
- Description should state the coverage percentage (reported by `validate-translations.js`) and whether a native speaker reviewed the translations.
- Link to any related issue with `Fixes #<issue>`.

## Community Translation Tool

Users can contribute new locales without writing code, entirely through the browser UI.

### For users

1. Open the **Language Switcher** in the top navigation bar.
2. Click **Community Translations**.
3. Click **Download Translation Template (JSON)** to get `en.json` as a starting point.
4. Translate the values in the file. Leave the keys and `{placeholder}` tokens unchanged.
5. Click **Upload & Preview Translation** and select your translated `.json` file. The app switches to your translation immediately so you can review it live.
6. Fill in the language name, your name, and optionally your email and notes.
7. Click **Submit Translation** to send it to the server (`POST /api/i18n/contribute`).

The response includes a **coverage percentage** and a list of any missing keys. Aim for 100% before submitting.

### For maintainers

Submitted translations are stored in a server-side in-memory array and are lost on server restart. To retrieve submitted entries:

```
GET /api/i18n/contribute
```

Response shape:

```json
{
  "success": true,
  "totalBaseKeys": 183,
  "template": { … },
  "submissionsCount": 2,
  "submissions": [
    {
      "id": "contrib_1700000000000_ab1cd",
      "locale": "it",
      "languageName": "Italian",
      "direction": "ltr",
      "contributorName": "Maria Rossi",
      "submittedAt": "2026-09-26T10:00:00.000Z",
      "coveragePercent": 97
    }
  ]
}
```

To promote a community submission to a built-in locale, follow the [PR workflow](#adding-a-new-locale-pr-workflow) using the downloaded translation JSON as the locale file.

> **Note**: Community submissions are ephemeral — not stored in a database. If you want to preserve a contribution, export it from the API before the server restarts.

## Translation Tooling

### `scripts/validate-translations.js`

Validates that every leaf key in `en.json` is present in all other locale files. Run it before committing locale changes.

```bash
node scripts/validate-translations.js
# or
npm run validate:translations
```

Output on success:
```
✅ All translation keys are present in all locale files.
```

Output on failure (exits with code 1):
```
❌ Missing keys in de.json:
   - wallet.activate_account
   - i18n.missing_keys
```

The script currently validates `es`, `fr`, and `pt`. When you add a new locale via PR, add its code to the `otherLocales` array at the top of the script:

```js
// scripts/validate-translations.js
const otherLocales = ['es', 'fr', 'pt', 'de', 'ar', 'it']; // ← add new locale here
```

> The script checks key presence but not translation quality. Human review is still required.

### `GET /api/i18n/contribute`

Returns the full `en.json` schema along with a list of community submissions and the total key count. Useful for contributors who want to check how many keys they need to translate.

### `__tests__/lib/i18n.test.ts`

Unit test suite covering:
- `translate()` — key lookup, interpolation, fallback to English, raw key return
- `detectBrowserLocale()` — exact match, prefix match, no match
- `registerCommunityTranslations()` — runtime locale registration

Run with:
```bash
npm test __tests__/lib/i18n.test.ts
```

## Number & Date Formatting

Number and date formatting is handled separately from the translation system using the browser's `Intl` API.

### Number formatting (`app/lib/formatAmount.ts`)

`formatAmount()`, `formatXLM()`, and `formatUSD()` use `Intl.NumberFormat` and default to `navigator.language` (the OS/browser locale) if no explicit locale is passed. This means number formatting follows the user's OS preference, which may differ from the app's active translation locale.

To format a number in a specific locale:

```ts
import { formatAmount } from "@/app/lib/formatAmount";

formatAmount(1234.56, { locale: "de-DE" })  // "1.234,56"
formatAmount(1234.56, { locale: "en-US" })  // "1,234.56"
```

### Date formatting (`app/lib/date.ts`)

`formatDisplayDate()` and `formatDateTime()` currently use `Intl.DateTimeFormat` hardcoded to `"en-US"`. Date output is always in English-US format regardless of the active locale. This is a known limitation — see [Known Limitations](#known-limitations).

## Known Limitations

| # | Issue | Impact |
|---|---|---|
| 1 | **No server-side translations** | SSR HTML renders with `lang="en"`. Translated content only appears after client hydration. SEO and screen readers see English on first render. |
| 2 | **No pluralization** | English-only ad-hoc pluralization (e.g. `clip${n !== 1 ? "s" : ""}`) is used in several places. Other languages may see grammatically incorrect plural forms. |
| 3 | **Date formatting hardcoded to `en-US`** | `formatDisplayDate()` and `formatDateTime()` always produce English-US dates. |
| 4 | **`validate-translations.js` not in CI** | Missing keys in `de.json` or `ar.json` are not caught automatically. Run `npm run validate:translations` manually before merging locale changes. |
| 5 | **Community submissions are ephemeral** | `POST /api/i18n/contribute` stores in memory only. Submissions are lost on server restart. |
| 6 | **Widespread hardcoded English strings** | Many UI strings are still not routed through `t()`. Tracked in issue #757. |
